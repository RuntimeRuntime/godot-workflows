# Change a Godot project

Read the game's instructions, profile and affected native scenes/resources/scripts.
Existing project decisions and user requirements take precedence over reusable
defaults. A profile is optional during exploration; a verification claim needs a
declared scope and known engine/tool identities.

Establish the requested outcome and concrete acceptance examples. For substantive
scene, dependency or state changes, use [feature planning](feature-planning.md).
Select relevant branches of the three skills and [verification](verification.md).
Small edits need only their affected decisions. Existing generic implementation,
diagnosis and review practices remain usable; this toolkit adds Godot evidence.

Implement a coherent change. Keep fixed content editable in native scenes and
Resources where appropriate. Run relevant fast checks while working. Tests should
exercise the real scene contract and expected player behavior.

Validate the combined source state. Assign an acquisition executor and name the
actual observer for required editor/play scenarios. Inspect existing evidence
before asking for recapture. Use [review](review.md) when a consequential risk
needs another judgment; choose lenses instead of a standing committee.

Close with the outcome, changed artifacts, supported exceptions, observations,
unresolved findings and limits. A verified claim needs current required evidence.
An explicit owner acceptance of a demonstrated risk retains failed results.
Task completion does not independently authorize publication or release.
