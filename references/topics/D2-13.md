# D2-13 — 2D particle effects

When: Create sparks, smoke, rain, magic, debris, trails, ambient motion or other many-instance visual effects.

Native candidates: `GPUParticles2D`, `CPUParticles2D`, `ParticleProcessMaterial`, `CanvasItemMaterial`, `LightOccluder2D`.

## Approach

Start with GPUParticles2D and a ParticleProcessMaterial for a configurable 2D emitter; use an authored texture or flipbook and set local/global coordinates, one-shot, lifetime, amount and visibility bounds to suit the effect. Consider CPUParticles2D only for a demonstrated target/rendering constraint or required behavior after checking that version's class docs.

Use native particle emission/randomness/curves and flipbooks instead of scripting each short-lived cosmetic particle as an independent Node2D. Keep individually interactive projectiles or gameplay entities as scenes/bodies when their identity and collision matter.

## Pitfalls

- GPUParticles2D do not collide with PhysicsBody2D; their optional collision path is against LightOccluder2D, so don't use them as physical projectiles.
- A one-shot GPU emitter may need `restart()` after its finished signal rather than setting emitting true immediately.
- Local versus global coordinates changes whether particles follow their emitter after emission.
- The 4.7 2D particle tutorial is marked Work in progress; its CPU/GPU feature comparisons need pin-specific validation.

## Verify

- Preview the emitter and verify start, stop, one-shot completion/restart, draw order, scaling and local/global movement in play.
- Test the actual target renderer/device class and particle count; confirm the visibility rectangle does not cull visible particles.
- For fixed-seed visual tests, set and record the particle seed with fixed-seed enabled.

## Version and limits

GPUParticles2D and CPUParticles2D are documented separately in 4.7; the 4.7 particle workflow tutorial warns that it may be outdated. Avoid a universal CPU/GPU recommendation without target data.
