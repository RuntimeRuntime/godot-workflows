# SH-08 — Preferences and progression persistence

When: Saving player settings/remaps or game progression across scenes/sessions.

Native candidates: `ConfigFile`, `FileAccess`, `JSON`, `FileAccess.store_var/get_var`, `user://`, `res://`.

## Approach

Use ConfigFile for section/key user settings; define a project-owned progression contract using FileAccess with JSON for simple readable data or binary serialization when appropriate. Persist user data under user://.

Do not write into res:// in exported builds or treat in-memory changes as saved; do not copy the saving tutorial's sample as a universal save system.

## Pitfalls

- JSON cannot directly represent all Godot types.
- Save examples assume a particular object/group strategy and omit project-specific load setup.
- Missing/corrupt/older-version save behavior must be designed.

## Verify

- Save/relaunch/load representative settings and progression.
- Exercise malformed/missing/prior-version data.
- Verify target-specific user:// location and recovery behavior.

## Version and limits

Godot 4.7 docs; save schema/migration policy remains project-specific.

## Primary sources


- [FS18: ConfigFile class reference](https://docs.godotengine.org/en/4.7/classes/class_configfile.html). Scope/limits: A simple configuration helper, not a general save-game architecture.

- [FS19: Saving games](https://docs.godotengine.org/en/4.7/tutorials/io/saving_games.html). Scope/limits: Tutorial explicitly leaves larger save design to the project; sample has simplifying assumptions.

- [FS20: File system](https://docs.godotengine.org/en/4.7/tutorials/scripting/filesystem.html). Scope/limits: OS-specific user data folder names depend on project settings/target.
