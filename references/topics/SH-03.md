# SH-03 — InputMap actions, devices, and remapping

When: Adding controls, multiple input devices, per-player bindings, or runtime key remapping.

Native candidates: `InputMap`, `Input`, `InputEventKey`, `InputEventAction`.

## Approach

Define named actions and bind device events to them; use action polling for held state and InputEvents for discrete events. Persist runtime remaps explicitly in player settings.

Do not scatter raw key checks through gameplay or assume runtime InputMap state is saved; raw events remain suitable when the feature requires event-specific details.

## Pitfalls

- InputMap runtime changes are not automatically persisted.
- Built-in UI actions should stay separate from gameplay mappings.
- Input events can have device-specific properties and target limits.

## Verify

- For changed keyboard bindings, test fixed expected device events through InputEventKey → the saved InputMap → observable scene behavior. Set physical_keycode for physical bindings or keycode for logical bindings. Inject press/release events with Input.parse_input_event, allow relevant process/physics frames, and assert the resulting interaction. Keep expected keys independent of InputMap.action_get_events() so reversed or missing mappings fail. Release every injected key and restore input/focus state.
- Action-level tests (Input.action_press or InputEventAction) exercise downstream logic but bypass device bindings; pair them with the physical-event path when bindings are in scope.
- Keep visible interaction on each nominated real device/platform for window focus, layout, delivery and controller behavior. Injected events establish engine routing, not OS or hardware delivery.
- Remap and restart to check settings persistence.
- Confirm UI focus actions remain distinct.

## Version and limits

Godot 4.7 docs; verify physical devices and platform capabilities on target.
