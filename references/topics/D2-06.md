# D2-06 — AnimationPlayer, AnimationTree and authored transitions

When: Coordinate multiple animated properties, blend clips, represent state transitions, or layer/interrupt animations.

Native candidates: `AnimationPlayer`, `AnimationTree`, `Animation`, `AnimationNodeStateMachine`, `AnimationNodeBlendTree`, `AnimationNodeBlendSpace1D`, `AnimationNodeBlendSpace2D`.

## Approach

Store editable clips and property/method tracks in AnimationPlayer. Add AnimationTree when advanced blending, blend spaces, one-shots or state transitions are needed; AnimationTree references the AnimationPlayer's clips and does not store its own animations. Both systems work in 2D and 3D.

Avoid hand-maintaining clip timing/blending tables or custom cross-fade math when the editor's animation tracks and AnimationTree graph directly express the desired transitions. A single uncomplicated clip does not need an AnimationTree.

## Pitfalls

- AnimationTree must reference the intended AnimationPlayer and a connected output path; an unconnected graph produces no animation.
- Keep the gameplay state owner and animation presentation state coherent; an animation graph does not replace gameplay rules.
- Call-method animation events are not executed during editor preview for safety; preview is not proof of their runtime effect.

## Verify

- Inspect clip targets and tree graph in the editor; verify each intended state/transition and one-shot interruption at runtime.
- Test the real actor's movement/attack/hit/death transitions, including interruption and return-to-idle cases.
- Treat method-track side effects as runtime behavior and observe them in play.

## Version and limits

AnimationPlayer and AnimationTree apply to both dimensions; choose a 2D fixture for 2D property paths and verify process/callback modes on the pinned version.
