# D2-09 — Overlap sensors and collision filtering

When: Detect a player entering a pickup, hurtbox, trigger, proximity radius, gravity zone or other non-blocking region.

Native candidates: `Area2D`, `CollisionShape2D`, `CollisionPolygon2D`, `CollisionObject2D`, `CharacterBody2D`, `RigidBody2D`.

## Approach

Use Area2D with authored collision shape(s) and the appropriate body_entered/body_exited or area_entered/area_exited signal. Assign named collision layers and masks so each area queries only relevant object categories. For area-based gravity/damping changes, configure Space Override and priority deliberately.

Use the engine's overlap signals and collision filtering instead of polling distances against every actor or adding invisible solid bodies for detection alone. Use physics bodies when actual collision response/blocking is required.

## Pitfalls

- An Area2D detects overlap and can influence physics; it does not itself provide the solid movement response of a body.
- Use area signals when target is an Area2D and body signals when target is a PhysicsBody2D/CollisionObject2D; the signal's argument type and mask must match.
- Area2D layer/mask and monitoring settings can silently prevent intended signals.
- Overlapping areas with gravity/damping overrides are evaluated by priority and override mode.

## Verify

- Test entry, exit, staying-overlap and repeated overlap behavior using the actual collision shape.
- Check body-versus-area signal delivery and named layer/mask interactions with unrelated actors.
- If using gravity/damping overrides, enter/leave overlapping areas in different priority combinations and observe the result.

## Version and limits

Physics collision objects expose separate 2D and 3D types. The layer/mask model is shared conceptually; use the 2D project layer names and actual class references.
